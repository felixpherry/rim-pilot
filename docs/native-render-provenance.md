# Native render provenance

`RenderProvenance` is a host-testable authorization tracker; `GameNativeRender` supplies installed Unity/game-thread witnesses. `ScreenshotCapture` and `GameScreenshotBackend` now supply the bounded screenshot producer. No Mono/game/pixel acceptance is claimed; CLI image validation/output is separate work.

## Admission

A trusted capture owner arms one request after a fresh safe sample. The next complete frame must be strictly newer than that request. Evidence requires all of:

- Safe, ready, unchanged root/game scope and private hard safety epoch throughout witnessed boundaries; unchanged frame, dimensions and UI scale.
- Complete derived Root Update and Root OnGUI repaint, including both callback endpoints. Skipped originals and escaping exceptions invalidate. Error/assert/exception log notification also invalidates, because installed Root catches its own exceptions.
- **User-approved map-view divergence:** paused/live map capture uses weaker displayed-frame proof: the frame advanced past the request, this capture's GPU fence passed, and safety/readiness/scope/size/scale stayed clean throughout hold-then-release. The primary camera clears depth only; these images show what the game displayed for that frame, **not proof that every primary pixel was replaced**. Whole-frame provenance is guaranteed for menu capture only. `screenshot.map_view` is `available` when the screenshot producer binds (`unverified` otherwise), with `screenshot-v1` schema and a fixed proof-basis reason. Host/compile evidence is not paused/live pixel acceptance; real-game proof remains in the next paused/live batches. World/specialist capture remains unverified.
- Bounded, balanced camera pre-render/post-render callbacks. Pre-cull also samples safety. Nested/repeated/manual renders are conservatively unsupported. Outside approved map view, at least one camera must replace the full primary-display backbuffer with a color clear, witnessed before and after rendering. Skybox/depth-only/partial/offscreen clears do not establish removal of stale unsafe pixels.
- End-of-frame scheduling at the capture frame, then a **later** frame's passed native CPU graphics fence (inserted at pixel-processing stage right after the private readback), followed by a fresh game-thread safety/scope/geometry sample and an unchanged hard epoch. Neither Root.Update, WaitForEndOfFrame, capture API return nor fence alone supplies evidence: the fence only gates release of bytes admitted under their scene's proof basis. Map/world mode changes also revoke the request, including switch-away/back.

Ordinary Update/GUI brackets still revoke observation leases. Render provenance separately preserves its hard epoch across those brackets, requiring explicit endpoint witnesses instead. Developer/window mutations, current-map setter brackets (including switch-away/back), load/root/game/map changes, unsafe/incomplete samples and geometry discontinuities invalidate it irreversibly, including worker-thread transition notifications. A safe endpoint cannot resurrect an old request.

## Capture-owner contract

`ModBootstrap.NativeRender.Arm` accepts one trusted consumer. The consumer runs synchronously inside every eligible EOF callback (strictly newer than the request frame) with a short-lived `NativeRenderTicket`. Same-request-frame EOF is skipped without disarming. A frame that cannot be witnessed safe makes every ticket call refuse `not_ready` at once, so the client gets a clear refusal rather than waiting out the transport deadline.

**Hold then release (phase-4 divergence, plan.md).** On actual Mono (OpenGLCore, multithreaded rendering) the CPU fence never reports passed in the same EOF; it flips about two frames later. So:

1. **Capture EOF.** If the frame was not witnessed safe, nothing is read: the consumer may re-arm a fresh request (at most twice, same flight and cadence charge, before any bytes exist) and otherwise refuses `not_ready`. A witnessed frame gets the bounded private readback, then `ticket.Hold()`: scene-specific evidence (update, repaint, balanced cameras, plus full color clear outside map view) without the fence, then creates this capture's CPU fence. The bytes are encoded to PNG right away (so the release frame only builds the DTO), stay private and **unreleased**, owned by the one flight; the raw copy is dropped.
2. **Later EOFs.** Each callback re-witnesses the frame. If the fence is not passed yet, the flight just waits. When it passed, `ticket.Release(held)` rechecks, on the game thread, the same hard safety/readiness epoch, root/game scope and render size/scale (any unsafe interval between would have bumped the epoch), then the consumer encodes, calls `ticket.CheckRelease(stamp)` in that same callback and transfers primitives under the existing transition read fence. The reported frame is the capture frame whose pixels were read.
3. **Discard.** Any change, refusal, failed witness, cancel/disconnect, transition, readback/encode/release failure, or the 2-second flight limit drops the bytes, closes the fence state and rejects (`timeout` when the fence never passes). Nothing is released on fence alone, no spin, no GPU fallback, no second read.

Tickets close on callback exit; held bytes live in the flight, not in any ticket. The consumer must settle its pending request on cancellation/deadline even if no ticket can be offered. Exceptions revoke provenance; partial output is never completion. A same-EOF pass (fence already true when held) releases in that one callback.

Render callbacks spend no sample until the frame's own Begin made provenance active (previously the rest of the arm frame wasted a full safety sample per callback, exhausting the allowance and revoking the epoch). Install performs one discarded render sample (nothing armed) so first-use JIT of the sampling path is not charged to the first capture; its debit is not carried forward. Each finite safety/readiness boundary sample has an independent fixed 2-ms cooperative allowance; producer, event and capture debits cannot skip it. Failed/missing/overdue samples still revoke provenance. Sample cost is accounted separately from the unchanged shared 2-ms producer allowance (explicit phase-4 budget divergence). Fixed managed stages and synchronous native calls can still overrun between checks; native capture latency is a separate required measurement, not bounded by a stopwatch after return. No fence polling loop or extra request dispatch occurs in render callbacks.

## Bounded capture ownership

One flight per session, including EOF waiting, held bytes and failure cleanup. Held memory is at most one raw RGB24 frame (plus one transient PNG at release); the flight limit is 2 seconds, under the 3-second request deadline, and `Sweep` answers `timeout` rather than letting the transport time out silently. Attempts are at least 1,000 ms apart; overlapping/rate-limited requests get `busy`. Dispatcher keeps the active cancellation slot until EOF completion or discard. Deadline/disconnect/transition cleanup does not depend on receiving a ticket; no-ticket requests expire through the existing transport deadline and game-thread sweep. No unbounded capture queue or background Unity work.

Before any image allocation, validate width/height/pixels and exact worst-case PNG size. Read the whole existing primary backbuffer into one owned RGB24 texture with one mip; refuse a non-null active render target. `ReadPixels(..., false)` avoids mip generation; no Apply/upload, camera render, render-target assignment, scaling or UI mutation. Copy exactly `3 * width * height` raw bytes, then immediately destroy only that bridge-owned texture, including on errors. Native allocation/copy overhead remains platform-owned and needs measurement.

A bounded managed PNG encoder writes top-down RGB rows from Unity's bottom-up data, filter 0, stored DEFLATE blocks, Adler-32 and PNG CRCs. Exact output bytes are `63 + n + 5 * ceil(n / 65535)`, where `n = 3 * width * height + height`. This avoids calling an opaque native PNG encoder before knowing its allocation/output bound. Existing 1,920×1,080 / 2,073,600-pixel limits still apply, but **all** ceilings must fit: 1,280×720 fits; 1,920×1,080 refuses `response_too_large` before allocating. No lossy prefix/crop or desktop-capture fallback. PNG, base64/chunks and transport remain capped by the existing separate screenshot response profile.

Readback precedes `ticket.Hold()` (and so fence creation). Encoding and primitive DTO construction precede `ticket.CheckRelease()`, which must run in the very callback that released. A transition read fence spans each consumer callback, the final fresh sample and pending-read ownership transfer. Tickets cannot survive EOF; held bytes are released only by a later passing callback, never by the next ordinary update. All failures discard bytes.

### Explicit work-budget limitation

Ordinary producers retain the shared cooperative 2-ms allowance; safety boundary samples have their own fixed 2-ms allowance. Capture has a **separate 100-ms cooperative stage deadline**, checked around native work, between encoding blocks and before release. Full elapsed capture cost debits remaining shared work for later callbacks in the same update. This is an explicit work-budget divergence, **not** proof of a 2-ms capture or a 100-ms native limit: texture creation, ReadPixels, raw copy and destruction cannot be interrupted. Managed encoding/CRC/base64 also run synchronously in that EOF. If a stage returns overdue, no image is published; already-spent latency cannot be undone. Actual stage/total latency and acceptance remain unresolved until isolated runtime measurements. Do not treat host tests or stopwatch checks as native bounds.

## Installed-source audit and remaining proof

Fresh private inspection used the installed Root, Root_Play, Root_Entry and Game.CurrentMap implementations, Unity Camera callback dispatch and geometry/backbuffer properties, Graphics.CreateGraphicsFence, GraphicsFence.passed and WaitForEndOfFrame, plus installed Harmony MethodCreator/InjectedParameter handling of finalizer `__runOriginal`. Root performs GUI work after Update and catches/logs internal failures; Unity camera callbacks originate in native-invoked managed dispatch. Fence validation checks platform support and native fence state. WaitForEndOfFrame itself is only a marker type. Capture implementation additionally inspected installed Texture2D constructor/mip-count forwarding, ReadPixels/readability/native binding, GetRawTextureData byte-array binding and Object.DestroyImmediate forwarding. Proprietary sources remain outside deliverables.

Native renderer/IMGUI scheduling, actual color-clear coverage, fence support/completion latency and full-profile callback compatibility still need serial isolated menu/paused/live pixel tests. Arbitrary third-party direct debug-field writes entirely inside unaudited callbacks cannot be generically witnessed; this is finite audited safety, not universal mod-debug redaction. Apart from the explicit user-approved map-view proof, unsupported rendering configurations must refuse rather than weaken provenance or silently switch capture routes.
